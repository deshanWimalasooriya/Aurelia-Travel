1. Introduction
1.1 Background and Problem
Busy working professionals frequently get short breaks of one to three days but lack the time to research transport, accommodation, activities and costs. Planning such a short trip across several websites leads to "analysis paralysis", uncertainty about the total cost and, often, a decision not to travel at all.
Aurelia Travel
 is a web platform that addresses this problem by combining two capabilities in one interface: a 
Smart Plan
 module that turns a start point, time window and budget into a day-by-day itinerary with a live budget, and a full 
hotel discovery and booking
 system. The platform also provides dedicated dashboards for 
hotel partners
 (property managers) and 
platform administrators
, so that every stakeholder in the booking chain uses the same product.
1.2 Objectives
Automated itineraries:
 generate a trip plan from a start location, destination, date, duration, transport preference and budget.
Financial transparency:
 show estimated and remaining budget that updates instantly when the user changes choices.
Frictionless booking:
 allow travellers to find, compare, save and book hotels in a small number of clear steps.
Partner self-service:
 let hotel managers publish properties and rooms, handle bookings and reviews, and settle commission themselves.
Platform governance:
 give administrators tools for moderation, user management, finance, configuration, support and audit logging.
1.3 Scope of this Report
This report documents the implemented product and evaluates it against the Assignment 02 evaluation criteria. Section 2 identifies the target users; Section 3 describes the architecture; Section 4 walks through every major screen with screenshots of the actual outputs; Section 5 evaluates the design against each HCI criterion (Section A of the rubric); Section 6 covers project completeness (Section B); Section 7 contains the demonstration plan and design justifications (Section C); and Section 8 lists limitations and future work. 2.3 How User Needs Shaped the Design
Time is the scarcest resource
 for the traveller persona, so the landing page leads with one primary call to action ("Generate My Trip"), the planner form has sensible defaults (round trip when no destination is given, a "surprise me" trip when no description is given) and the booking form is pre-filled from the user profile.
Cost certainty
 is shown continuously: the itinerary header displays remaining budget and estimated cost, and the value changes colour when the budget becomes low or negative.
Non-technical hotel partners
 get a single sidebar with plain labels (Overview, Hotels, Rooms, Bookings, Customers, Analytics, Reviews, Finance) and a repeated list-then-form pattern, so learning one screen teaches all of them.
Administrators
 work with large datasets, so every admin table has a search box, status badges and confirmation or OTP protection on destructive actions.

5. Evaluation Against HCI Principles and Guidelines
This section evaluates the product against each criterion in Section A of the evaluation rubric. For each criterion we explain the design decisions taken, the evidence in the implementation, and the weaknesses we identified during our own review. Figure references point to the screenshots in Section 4.
5.1 Usability and Ease of Use (10 marks)
The goal was that a first-time visitor should understand what the product does and complete a core task without instructions. We applied the principles of learnability, recognition rather than recall, and a strong single primary action per screen.
Design decision / HCI principle
How it is implemented in Aurelia Travel
Clear value proposition and primary action
The home hero states the product purpose in one line and offers one dominant button, "Generate My Trip" (Fig. 2). A "How it Works" section explains the process in three steps.
Recognition over recall
Every input is labelled with text plus an icon (map pin, calendar, wallet, car). Placeholders give examples, e.g. "e.g. Colombo", "e.g. 50000" (Fig. 3).
Direct manipulation
Locations can be set by clicking the map, and transport choices on the itinerary are changed in place with immediate cost updates (Figs. 3–4).
Familiar patterns
Hotel cards, filters, a rooms table and a stepped checkout follow conventions users already know from major booking websites, reducing learning effort (Figs. 6–11).
Sensible defaults
Two adults preselected; round trip if the destination is blank; a "surprise me" trip if no description is given; guest details pre-filled from the profile.
Identified weaknesses and planned improvements:
Some icon-only controls (e.g. edit/delete in admin tables) rely on tooltips; adding visible text labels on hover/focus would further improve learnability.
5.2 Consistency and Standards (8 marks)
Consistency was pursued at three levels: visual (colours, typography, icons), structural (page layouts and patterns) and behavioural (how controls respond).
Design decision / HCI principle
How it is implemented in Aurelia Travel
Shared layout components
All traveller pages share the same Header and Footer through a common Layout; both dashboards use a persistent left sidebar with the same structure.
One icon family
Lucide icons are used across the entire product, so the same concept always has the same icon (heart = save, ticket = bookings, map pin = location).
Design tokens
Colours are defined as CSS variables (themes.css) and reused for accents, stars and status colours; super-admin screens share a common "sa-" style set.
Repeated interaction pattern
Management screens (hotels, rooms, users) all use "searchable list → Add/Edit form → Cancel/Save", and modals always close with an X button in the top-right corner.
Consistent status language
Bookings, hotels and payments use the same colour-coded badges (green = confirmed/active, red = cancelled/inactive, amber = pending).
Platform conventions
Standard web conventions are respected: logo returns home, active navigation link is highlighted, underlined blue text for links, dates in native date pickers.
Identified weaknesses and planned improvements:
Currencies are mixed: the Smart Plan uses LKR, while hotel prices are in USD (the external hotel data source does not support LKR). A single display currency or a currency switch is planned.
Feedback style varies: some screens use inline messages while others use browser alert() pop-ups. These will be unified into one toast/inline notification component.
Hotel cards currently render two overlapping wishlist buttons; one will be removed to keep a single, consistent control.
5.3 Visibility, Feedback and System Status (8 marks)
Following Nielsen's first heuristic, the system should always keep users informed about what is happening through appropriate and timely feedback.
Design decision / HCI principle
How it is implemented in Aurelia Travel
Loading states
Skeleton cards and a hotel-details skeleton mirror the final layout while data loads (Fig. 7); the Search button changes to a spinner and is disabled during a search; "Loading your itineraries…" messages in lists.
Progress indication
The booking flow shows a three-step tracker where completed steps turn into check marks (Figs. 10–11). Multi-step modals (forgot password, commission payment) state the current step in the heading.
Live state
Remaining budget recalculates instantly and turns to a warning colour when low or negative (Figs. 4–5). The wishlist heart fills red and the header badge count updates immediately.
Real-time notifications
Socket.IO pushes notifications and chat messages; the bell shows an unread count and unread items have a dot (Figs. 14–15).
Location awareness
The active navigation item is highlighted; page titles and subtitles describe each screen; the header greets the user by name with the time of day and shows their role badge in the profile menu.
Action results
Success messages confirm completed actions (booking confirmed, review submitted, password reset); processing buttons are disabled to prevent double submission.
Identified weaknesses and planned improvements:
Several success/error messages use blocking alert() dialogs; non-blocking toasts would give the same feedback with less interruption.
5.4 Error Prevention, Recovery and User Control (10 marks)
We aimed first to make errors hard to make, then to make them easy to recover from, and to always give users an exit (Nielsen heuristics 3, 5 and 9).
Design decision / HCI principle
How it is implemented in Aurelia Travel
Constraint-based prevention
Required fields, typed inputs (email, number, date, datetime-local) and minimum values (adults ≥ 1, children ≥ 0) stop invalid input before submission. Only rooms marked active are offered for booking.
Validation with clear messages
Password length and confirmation are checked before any request, and server messages are shown in plain language ("Passwords do not match", "Please fill in all required fields (*)") (Fig. 17).
Guided correction
Pressing Reserve without selecting a room smoothly scrolls the user to the rooms table and tells them what to do.
Protection of work
After step 2 the booking is saved as a draft; if the page is closed the "Complete your booking!" tag lets the user resume at the confirmation step. The Remember-me option stores the email for the next sign-in.
Safe destructive actions
Deleting properties/rooms, banning users and clearing the wishlist require confirmation (Fig. 34); deleting a hotel in the admin console additionally requires an OTP.
Recovery paths
Password recovery with code resend; "Not you?" and Sign-in options on the booking page; Cancel buttons on every form and modal; "Back" and "Clear Filters" actions; empty states that suggest the next step.
Access control
Route guards redirect users away from pages they cannot use instead of showing broken screens; rate limiting returns a readable "please slow down" message.
Identified weaknesses and planned improvements:
Check-out date is not yet restricted to be after the check-in date in all date pickers; a min-date constraint and inline date error will be added.
Deleted itinerary items cannot yet be undone; an "Undo" snackbar is planned for the trip dashboard.
5.5 Layout, Navigation and Information Organisation (10 marks)
Information architecture is organised by user role and by task frequency, with a visual hierarchy that leads from the most important information to the details.
Design decision / HCI principle
How it is implemented in Aurelia Travel
Shallow, role-based navigation
The traveller top bar has only five items (Home, Smart Plan, Hotels, About, Contact). Personal items (My Account, My Reviews, My Bookings, Saved Properties) are grouped in the profile dropdown, and dashboard links appear only for users who have that role.
Clear page hierarchy
Hotel details flow from summary (name, rating, price) → visuals (gallery + map) → decision information (services, rules) → action (rooms table and reserve) → social proof (reviews) (Figs. 8–9).
Grouping and proximity
Related fields are grouped in rows (locations; date + transport; duration + budget). House rules are listed in a dedicated box, and filters are grouped under headed cards (Price, Rating, Facilities).
Persistent context
The booking summary stays fixed on the left in a 25/75 split so users never lose sight of what they are paying for (Fig. 10).
Dashboard organisation
Sidebars follow the order of the manager's workflow (Overview → Hotels → Rooms → Bookings → Customers → Analytics → Reviews → Finance), and KPIs are placed above detailed charts and tables.
Navigation state
Search parameters are placed in the URL, so results can be bookmarked or refreshed; the mobile menu closes automatically after navigation.
Identified weaknesses and planned improvements:
The Hotels entry currently leads to a few similar listing pages (showcase, search, hotels); these will be merged into one listing to avoid duplicate paths.
5.6 Visual Design, Readability and Accessibility (8 marks)
The visual design aims for a calm, premium look that keeps text readable and highlights actions, while supporting a range of users and devices.
Design decision / HCI principle
How it is implemented in Aurelia Travel
Visual hierarchy
Large headings, generous white space, card-based grouping and one accent colour for primary actions guide the eye to the next step.
Readability
Sans-serif typography, dark text on light backgrounds, and a semi-transparent tint over the Smart Plan map so the form stays readable over map tiles. The wishlist button uses a white background and shadow to remain visible on bright photos.
Colour with redundancy
Status is shown by colour and also by text (e.g. "Confirmed", "Allowed / Not Allowed"), so information is not lost for colour-blind users.
Accessible markup
Form labels are linked to inputs (htmlFor/id) on the authentication page; images have alt text; the mobile menu button has an aria-label; native form controls keep keyboard support.
Responsive design
Layouts adapt to mobile: collapsed navigation, slide-in filter panel and stacked cards (Fig. 19).
Seasonal theming
A theme provider applies a month-based data-theme attribute, allowing the colour palette to change seasonally while using the same tokens.
Identified weaknesses and planned improvements:
The hotel gallery uses clickable background-image blocks that are not reachable by keyboard; these will become buttons with alt text.
Colour contrast of some light grey helper text should be verified against WCAG 2.1 AA (4.5:1).
Reduced-motion support (prefers-reduced-motion) should be added for the intro animation and scroll effects.
5.7 Efficiency and Interaction Design (8 marks)
For frequent and time-pressed users we minimised the number of steps and the amount of typing required to finish each task.
Design decision / HCI principle
How it is implemented in Aurelia Travel
Minimal input
A full trip needs only a start point, date and budget; everything else has a default. Guest details are auto-filled; Google sign-in avoids creating a password.
Shortcuts and accelerators
Map click fills coordinates and automatically moves on to the destination; "Remember me" pre-fills the email; the header heart jumps straight to saved hotels; admin tables have instant search.
Instant computation
Nights, room quantity and total price are calculated automatically; budget and cost recalculate on every change without a "calculate" button.
Fewer page loads
Login, registration and password reset share one page; room details and gallery open in modals; edit forms open in a sidebar on the trip dashboard.
Efficient data browsing
Filters, sorting and pagination (8 hotels per page) keep result lists manageable; "Mark all read" clears notifications in one click.
Identified weaknesses and planned improvements:
Dates chosen on the search form could be carried automatically into the hotel details page to avoid entering them twice.
5.8 User-Centred Design and Target-User Suitability (8 marks)
The product is built around the three personas in Section 2, and each screen can be traced to a user task.
Design decision / HCI principle
How it is implemented in Aurelia Travel
Busy traveller
1–3 day durations only, a budget-first planner, a "surprise me" option and a live budget directly target the "short getaway" persona.
Local context
The map is centred on Sri Lanka, the budget is entered in LKR, and transport options include tuk-tuk and public bus, reflecting how local users actually travel.
Trust and safety
Reviews and ratings, house rules, a Safety Center, dispute resolution, two-step verification and live support address the anxiety of booking with a new platform.
Hotel partner
Self-service onboarding, rich property and room forms, review replies and a transparent commission hub match the needs of non-technical managers.
Administrator
Search on every table, bulk visibility of status, activity logs and configurable commission support efficient, accountable platform management.
Identified weaknesses and planned improvements:
A formal usability test with 5–8 representative users (task success rate, time on task and SUS score) is planned to validate these design decisions with real data.

7.2 Anticipated Questions and Answers
Q: Why did you separate the system into three role-based areas?
A: Each persona has different goals and skills. Separate areas keep the traveller interface simple (five navigation items) while giving managers and admins dense, tool-like screens. Links to dashboards appear only for users with the right role, so travellers are never exposed to irrelevant complexity.
Q: How does the system keep users informed?
A: Through skeleton loaders, disabled/spinning buttons, a three-step booking tracker, a live budget widget with colour warnings, and real-time notification and chat updates via Socket.IO.
Q: What happens if a user makes a mistake while booking?
A: Invalid input is blocked by required and typed fields; missing selections are explained and the page scrolls to the right place; the booking is saved as a draft after the details step so it can be resumed; Cancel/Back options are always available.
Q: Why use a map for location input?
A: Many travellers know where they want to go visually but not the exact place name. Clicking the map is faster and avoids spelling errors, while typing remains available as an alternative for users who prefer it.
Q: How did you address accessibility?
A: Labelled form controls, alt text on images, an aria-label on the menu button, status shown by both colour and text, responsive layouts and native inputs with keyboard support. We also identified remaining gaps (keyboard access to the gallery, contrast checks, reduced motion) and planned fixes.
Q: Why is the booking summary fixed on the left?
A: It applies "recognition rather than recall": users can check the hotel, dates and price at any moment without navigating back, which reduces anxiety and errors before payment.
Q: How do you protect against destructive admin actions?
A: Confirmation dialogs for deletes and bans, OTP verification for hotel deletion, publish/hide instead of delete where possible, and an activity log that records who did what.
Q: What would you improve next?
A: Unify feedback into toasts, use a single currency display, add date-range validation and undo, complete AI itinerary persistence, and run a formal usability study with SUS scoring.

9. Conclusion
Aurelia Travel delivers a working, integrated platform for three user groups: travellers who want to plan and book short trips quickly, hotel partners who need simple self-service management, and administrators who govern the platform. The design applies established HCI principles throughout: a clear single primary action, recognisable patterns, continuous feedback, error prevention with recoverable flows, a shallow role-based navigation and a clean, responsive visual design. The self-evaluation in Sections 5 and 8 also identifies concrete improvements, which together form a clear roadmap for the next iteration.
